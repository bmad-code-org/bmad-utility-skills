# Good Points Log — av-hitl-review Design
## Session: 2026-03-16

_Hardened thoughts logged below._

---

1. **Post-hardening review companion** — assumes code already survived adversarial machine review. Job is human confidence to merge or kill, not finding more bugs.
2. **Commit is the handoff** — cold-starts from branch/commit. No coupling to quick-dev internals. Works on any committed change from any source.
3. **Invocation IS the routing** — not invoking = glance mode (human just looks at diff). Invoking = full guided experience. No internal routing question.
4. **Conversation layer, not diff viewer** — human's diff tool handles visual presentation. Skill provides context, questions, findings, and re-review alongside it.
5. **Primary objective is design coherence, not correctness** — "correct" is handled by machine hardening. The human's irreplaceable value is evaluating whether the change is the right design decision for the system. The skill exists to activate that judgment.
6. **Correctness review is a separate, optional stage** — human-triggered when the change warrants it. Benefits from design review having already loaded the full mental model. This is where findings (including borderline/rejected) are surfaced and targeted re-reviews launched. Human spots the area of concern, LLM hammers the details.
7. **Engagement through reframing, not ceremony** — the anti-rubber-stamp mechanism is making the review inherently engaging by framing it as a design conversation. The process itself sustains attention, not forced gates or quizzes.
8. **[PROVISIONAL] Deviation-detection reviewer for design review phase** — an LLM adversarial pass focused on flagging pattern deviations and structural novelty (not defects) to guide the human's attention during design review. The LLM detects deviation, the human judges significance. Promising but unproven — needs a dedicated deep research pass on whether LLMs can reliably do this without creating automation bias on the significance filter itself. DO NOT ship without that research.
9. **Four review phases: Orientation → Walkthrough → [Detail Pass] → [Testing Nudge]** — Orientation: load the why, the context, the existing code the change lives in (no diff yet). Walkthrough: walk the change top-down organized by concern not by file — this is the main event where design judgment happens ("is this how I'd solve this problem?"). Detail Pass: optional, human-triggered — "you've seen the change, it seems right, but have you thought about X?" Findings, edge cases, deferrals, targeted re-reviews live here. Testing Nudge: optional, human-triggered — what was tested, what commands to run, what can't be tested automatically.
10. **The spec IS the review trail** — quick-dev evolves to produce a spec whose Code Map section is an ordered, navigable trail of clickable `file:line` stops with brief framing, sequenced by concern for comprehension. Orientation and walkthrough material are embedded in the spec. This makes the spec useful without any skill — a competent dev can just read it and click links (glance-plus). The agent already has this knowledge at the end of implementation; serializing it is cheap.
11. **Every code reference is a clickable `file:line` link** — core ergonomic, not a nice-to-have. Every time the skill (or the spec) references code, it uses `path:line` format that editors auto-link.
12. **The skill is the interactive layer on top of a self-sufficient spec** — the spec handles orientation and walkthrough as a document. The skill adds the conversation: detail pass, findings, targeted re-reviews, on-demand Q&A during any phase. Spec is the 90% solution, skill is the 10% power tool.
13. **Detail pass v1: "did you look at this?"** — the skill identifies 2–5 highest-stakes spots in the diff, weighted by risk over complexity. A trivial change to auth is more interesting than a complex change to a logging utility — complexity is visible in the diff, but risk context isn't. Each spot is one line: clickable `file:line` link, short risk tag (e.g. [auth], [public API], [schema]), one-phrase reason. No paragraphs. LLM detects risk category by pattern (auth/DB/billing/public API/infra), human judges significance. Effectiveness is unknown — treat as experiment, iterate.
14. **Skill generates the trail as fallback** — if no spec with embedded trail exists (hand-written code, different agent, lost spec), the skill builds the trail itself from the diff and codebase context. Slower and probably lower quality than author-produced, but still far better than no trail.
15. **Lenient entry point — assess what you have, fill gaps** — the skill handles a spectrum from "full spec with trail" (go straight into review) to "just a commit" (build trail from diff) to "vague notion" (gather intent from the human first). Light discovery step at the front assesses available artifacts and fills in what's missing before starting the phases.
16. **Trail includes rejected alternatives** — "the agent considered X but chose Y because Z." This is part of the trail, produced by quick-dev. Directly activates design judgment by making the decision space visible, not just the chosen path.
17. **Orientation starts with intent, capped at 200 tokens** — if the spec's intent section is under 200 tokens, show it as-is. If over, distill to under 200 and link to the full thing. Summary is of the *intent* (why and what), not the implementation. 200 tokens ≈ 20-25 seconds of reading for a developer scanning technical content. Only applies when intent is long or comes from a non-quick-dev source — quick-dev's template already constrains intent to a few sentences.
18. **Surface area signal at the top of orientation** — not a time estimate, but a stat line the human can read instantly: files changed, modules touched, lines of logic (not formatting/imports), whether it crosses architectural boundaries, any new public interfaces. The human translates surface area into their own effort estimate. Cheap, verifiable, no LLM judgment required.
19. **Testing nudge is a separate optional phase, not part of detail pass** — not about CI or test suites (assumed handled). Not "you should test this" but "you could see this working." If the change has user-visible behavior, the skill tells the human how they could observe it. Human decides whether it's worth their time.
20. **Front-load then shut up** — the skill presents the full trail (orientation + walkthrough) all at once. Human reads, clicks, navigates at their own pace. Skill only speaks again to nudge detail pass and testing when the human signals they're done (or asks a question). Minimize agent-initiated turns. Human drives everything after the initial presentation.
21. **Phase transition breadcrumb** — when moving to the next phase, lead with a one-liner showing progress, e.g. `Orientation → Walkthrough → [Detail Pass] → Testing`. Only at transitions, not on every message. Quick "you are here" reminder that there's more to go.
22. **[FUTURE] Visual structural representations** — Mermaid diagrams, dependency graphs for multi-module changes. Definitely valuable for hard-to-think-about structures. How and when to generate them is a whole separate subject. Not v1.
